# FaLe One API: Drive + Fotos (contract v1)

This contract covers the end-to-end encrypted cloud drive and photo backup of the FaleNetwork (FaLe Drive + FaLe Fotos), built on the FaLe-Konto.

The server never sees names, MIME types, plaintext sizes, capture dates, EXIF/GPS data, thumbnails or content. It stores only opaque ids, wrapped keys, encrypted envelopes and ciphertext chunks.

| Part | Location |
|---|---|
| Server | `api/drive/index.js` → `api/_lib/drive.js` (handler), `drivestore.js` (SQL RPCs), `blobstore.js` + `s3.js` (chunk storage) |
| Database | `supabase/migrations/20261015220000_fale_one_drive.sql`, `…220100_fale_one_drive_cron.sql`; Notfallzugang: `20261016090000_fale_one_emergency.sql`, `…090100_fale_one_emergency_cron.sql` |
| Notfallzugang (§12) | `api/_lib/emergency.js` (`em.*` actions), `api/_lib/notify.js` (pluggable notifier) |
| Reference client | `js/one/crypto.js` (format, normative), `js/one/api.js` (transport + client algorithms). ES modules, WebCrypto, no dependencies; they run in browsers and Node ≥ 20. |

Words like **must** are normative. When this text and `js/one/crypto.js` disagree, the code wins and this document has a bug.

## 1. Switching it on

The API answers `503 drive_not_configured` until all of the following hold:

- `ACCOUNTS_ENABLED=1`, with `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `FALE_RPC_SECRET` (≥ 32 characters), `FALE_TOKEN_SECRET` and `FALE_IP_SALT` set. These are the existing FaLe-Konto settings.
- `ONE_ENABLED=1`. This is new and defaults to off, so turning on the FaLe-Konto for FaLe PDF does not expose the drive by accident.
- Migration `20261015220000_fale_one_drive.sql` is applied. A missing SQL function is also mapped to `503 drive_not_configured`.

`POST /api/drive?a=config` works without authentication. It tells the app whether to show FaLe One at all.

## 2. Transport

| | |
|---|---|
| Base URL | `https://fale-pdf.vercel.app` (the API lives in the FaLe PDF Vercel project; the FaLe One web app may be hosted elsewhere) |
| Endpoint | `POST /api/drive?a=<action>` (the only exception: `GET …?a=gc` for the cron worker) |
| Auth | `Authorization: Bearer <FaLe-Konto access token>` (Supabase Auth JWT; ES256 is verified locally against JWKS, with a fallback to `/auth/v1/user`; anonymous sessions are refused) |
| Body | JSON (`Content-Type: application/json`, ≤ 256 KiB). Exceptions: `upload.put` sends the raw ciphertext chunk (`application/octet-stream`, ≤ `chunkSize`), and `get` sends an empty body and returns raw bytes. |
| CORS | Strict allow-list, no credentials. Allowed by default: `https://fale-pdf.vercel.app`, `https://fale-one.vercel.app`, `https://one.fale.network`, `capacitor://localhost`, `https://localhost`, `http://localhost`. `http://localhost:<port>` and `http://127.0.0.1:<port>` are allowed only outside production. `FALE_ONE_ORIGINS` (comma-separated) **replaces** the two FaLe One defaults, and `AI_ALLOWED_ORIGINS` adds further origins. Allowed request headers: `Content-Type, Authorization, X-Fale-Auth`; methods `POST, OPTIONS`. Preflight is cached for 2 h. |
| Ids | Node, revision and album ids are **lowercase** UUID strings generated by the client (v4, `crypto.randomUUID()`). Upload/blob ids are generated by the server. Ids are part of the AAD, so the canonical lowercase form is mandatory and other forms get `400`. |
| Encrypted fields | `key`, `meta` and `rev.key`/`rev.meta` are base64url without padding (`[A-Za-z0-9_-]`). Wrapped keys are 40–200 characters; envelopes are 24 to `limits.maxMetaChars` (16 384) characters. |

### Errors

Every error is JSON:

```json
{ "ok": false, "error": "<code>", "message": "<German text for users>", "...extra": "…" }
```

| HTTP | `error` | Meaning / extra fields |
|---|---|---|
| 400 | `bad_input`, `bad_size` (`want`), `bad_index`, `bad_json`, `unknown_action` | Invalid request. Do not retry unchanged. |
| 401 | `invalid_account` | Missing, expired or forged token. Refresh the session once, then sign in again. |
| 401 | `no_user` | The auth user no longer exists (the account was deleted). |
| 403 | `forbidden` | `gc` without the cron secret. |
| 404 | `not_found` | Unknown **or foreign** id. Both look identical, so ids cannot be enumerated. |
| 404 | `no_upload` | The upload session is unknown, expired, already committed or foreign. |
| 405 | `method_not_allowed` | |
| 409 | `conflict` | Optimistic concurrency failed. `node` (or `album`) carries the **current** server state. |
| 409 | `exists`, `trashed`, `not_trashed`, `bad_parent`, `cycle`, `too_deep`, `incomplete`, `too_many`, `is_head`, `not_direct` | See the individual actions. |
| 413 | `too_large` (`max`) | File, thumbnail or chunk too big. |
| 429 | `drive_limit` | Daily limit reached (per account or per IP); it resets at midnight Europe/Berlin. |
| 429 | `too_many_pending` | More than 256 open upload sessions. |
| 502 | `storage_unavailable` | The S3 backend is not reachable. Retry. |
| 503 | `drive_not_configured` | See §1. |
| 503 | `capacity` | The global beta storage is full. Retry later. |
| 507 | `quota_exceeded` (`used`, `quota`) | The account is full. The account is read-only (§6). Nothing is ever deleted. |
| 500 | `internal` | Retry with backoff. Internal details are never echoed. |

The reference client retries `0` (network), `502`, `503` and `504` with exponential backoff, and refreshes the token once on `401 invalid_account`.

## 3. Objects

All objects come back from the API in camelCase. Every numeric field is a JSON number.

```ts
type Node = {
  t: 'node'; id: uuid; parent: uuid | null /* null = root */; kind: 'folder' | 'file' | 'photo';
  version: number;          // optimistic-concurrency token, +1 on every change of this node
  seq: number;              // position in the change feed (unique, increasing per account)
  key: string | null;       // wrapped node key (§5.3); null only for tombstones
  meta: string | null;      // encrypted node metadata (§5.4); null only for tombstones
  createdAt: string; updatedAt: string;              // ISO timestamps (server time)
  trashedAt: string | null; trashRoot: uuid | null;  // in the trash; trashRoot = the node the user trashed
  deleted: boolean;         // tombstone: deleted forever (kept 30 days in the feed)
  head: Revision | null;    // current version (null for folders and tombstones)
  revisions?: Revision[];   // export only
};
type Revision = {
  id: uuid; key: string /* wrapped file key */; meta: string /* encrypted revision metadata */;
  hash: string | null;      // keyed content hash (§5.7), 43 chars
  size: number;             // ciphertext bytes of all its blobs (counts against the quota)
  deviceId: string | null; createdAt: string; supersededAt: string | null; head?: boolean /* versions only */;
  blobs: Blob[];            // exactly one 'content', optionally one 'thumb' and one 'preview'
};
type Blob = { id: uuid; purpose: 'content' | 'thumb' | 'preview'; size: number /* ciphertext */; chunks: number; chunkSize: number; backend: 'pg' | 's3' };
type Album = { t: 'album'; id: uuid; version: number; seq: number; key: string | null; meta: string | null; createdAt: string; updatedAt: string; deleted: boolean; items?: uuid[] /* export only */ };
type Member = { t: 'member'; album: uuid; node: uuid; seq: number; addedAt: string; removed: boolean };
```

**Data model in one paragraph.**

- A *node* is a folder, file or photo in one tree per account.
- A file or photo has one current *revision* (`head`) plus up to 10 older ones.
- A revision owns 1–3 immutable *blobs*: the content and optional thumbnail and preview. Each blob is a sequence of ciphertext chunks.
- *Albums* are encrypted names plus an id-only membership list of file/photo nodes. A photo can be in many albums and stays in its folder.
- *Backup devices* report heartbeats.
- Everything a device needs to rebuild its local index arrives through one *change feed* (§4.2, §7.4).

## 4. Actions

Request bodies are shown in full. Fields marked `?` are optional. Every response carries `"ok": true`.

### 4.1 `config` (no auth)

`{}` → `{ ok, configured, chunkSize, backend: 'pg'|'s3', direct, maxThumbBatch: 100, maxChangesPage: 1000, version: 1, emergency, notify }`

`emergency` is true when the Notfallzugang actions are available (§12); `notify` is true only when a mail provider is configured, so apps can say honestly whether anyone gets an e-mail.

`chunkSize` is the ciphertext bytes per chunk (default 1 048 576 = 1 MiB, set by `ONE_CHUNK_KB`, 64 KiB–4 MiB). Clients **must** use the value from here or from `quota`, never a constant.

### 4.2 `quota`, `changes`

**`quota`**: `{ detail?: boolean = true }` →

```json
{ "quota": 2147483648, "used": 123, "readOnly": false,
  "usage": { "files": 0, "versions": 0, "trash": 0, "pending": 0, "meta": 0, "total": 0 },
  "nodes": 0, "cursor": 0, "minCursor": 0, "chunkSize": 1048576, "backend": "pg", "direct": false,
  "limits": { "maxFileBytes": …, "thumbMaxBytes": 131072, "previewMaxBytes": …, "maxMetaChars": 16384, "maxPending": 256,
              "trashDays": 30, "versionDays": 30, "versionKeep": 10, "uploadTtlHours": 24, "backupWarnDays": 3 } }
```

- `used` covers everything stored for the account: current files, old versions, trash, open uploads (reserved), and keys plus envelopes.
- `usage` is the same total broken down by category. It is omitted when `detail: false`, which is cheaper.
- `readOnly` means `used ≥ quota`.

**`changes`**: `{ cursor?: number = 0, limit?: 1..1000 = 500 }` → `{ reset, changes: (Node|Album|Member)[], cursor, more }`

- The feed returns every node, album and membership whose `seq > cursor`, oldest first. It shows each item's **latest** state, so intermediate states are collapsed.
- `cursor` in the response is the highest `seq` returned. Continue while `more` is true.
- `reset: true` means the given cursor is older than the server's tombstone horizon (`minCursor`). The client **must** discard its local index and resync from `cursor = 0` (§7.4).
- Cursor safety: sequence numbers are drawn under a per-account lock inside the writing transaction, so a change with a smaller `seq` can never become visible after a larger one. A page boundary therefore never skips anything.

### 4.3 Folders and metadata

**`mkdir`**: `{ nodeId, parentId?: uuid|null, key, meta }` → `{ node }`

- The parent must be an existing folder of this account that is not in the trash (otherwise `409 bad_parent`).
- Retrying the identical request is idempotent. The same id with different content returns `409 exists`.

**`update`** (move and/or rename/edit metadata): `{ nodeId, baseVersion, parentId?: uuid|null, meta? }` → `{ node }`

- The *presence* of `parentId`, even as `null` (which means root), means "move".
- `meta` replaces the node envelope.
- At least one of `parentId` or `meta` is required.
- Errors:
  - `409 conflict` (+`node`) when `baseVersion ≠ node.version`.
  - `409 trashed`.
  - `409 bad_parent`.
  - `409 cycle` when a folder would move into itself or its subtree.
  - `409 too_deep` beyond 128 levels.

### 4.4 Uploads (resumable)

**`upload.create`**: `{ purpose: 'content'|'thumb'|'preview' = 'content', size, chunks, hash? }` →

```json
{ "uploadId": "<uuid>", "purpose": "content", "size": 300140, "chunks": 1, "chunkSize": 1048576,
  "backend": "pg" | "s3", "direct": false, "expiresAt": "…", "duplicates": ["<nodeId>", …] }
```

- `size` is the **ciphertext** size, so `chunks` must be `ceil(size / chunkSize)` (otherwise `400`).
- The quota is checked **and reserved** here, which is why open uploads count in `usage.pending`.
- Limits:
  - content: `limits.maxFileBytes`
  - preview: `limits.previewMaxBytes`
  - thumb: `limits.thumbMaxBytes` and exactly one chunk
- `hash` is the keyed content hash. When given, `duplicates` lists nodes that are not trashed and whose current version has the same hash. The response is informative only.
- Sessions expire after `uploadTtlHours` (24 h). Expired sessions are purged with their chunks.
- Thumbnails are always stored in Postgres, even with `BLOBSTORE=s3`.

**`upload.put`**: `POST /api/drive?a=upload.put&u=<uploadId>&i=<index>` with the raw ciphertext chunk as body → `{ ok }`

- Every chunk except the last must be exactly `chunkSize`. The last must be `size − (chunks−1)·chunkSize`. Otherwise `400 bad_size` (`want`).
- Chunks may arrive **in any order and any number of times**. The last write wins, and the content is identical anyway.
- After commit, or for a foreign or expired session, the answer is `404 no_upload`.

**`upload.urls`** (only when `direct` is true, i.e. S3): `{ uploadId, from?: 0, count?: 1..200 = 100 }` → `{ urls: [{ i, size, url, method: 'PUT', headers: { 'Content-Length': '…' } }], expiresIn }`

The client PUTs each chunk straight to the bucket. `Content-Length` is part of the signature, so exactly `size` bytes must be sent.

**`upload.status`**: `{ uploadId }` → `{ uploadId, status: 'pending'|'live', purpose, backend, size, chunks, chunkSize, expiresAt, expired, received: number[] }`

Resume by sending the chunks that are missing from `received`.

**`upload.abort`**: `{ uploadId }` → `{ deleted }`. This releases the reservation. Bucket objects are queued for the gc worker.

**`commit`**: creates a node with its first revision, or adds a new revision to an existing node.

```json
{ "nodeId": "<uuid>", "parentId": "<uuid>|null", "kind": "file"|"photo", "baseVersion": 0,
  "key": "<wrapped node key: required when baseVersion = 0, else optional and must equal the stored one>",
  "meta": "<node envelope: required when baseVersion = 0, else optional (replaces the name/EXIF envelope)>",
  "rev": { "id": "<uuid>", "key": "<wrapped file key>", "meta": "<revision envelope>", "hash": "<43 chars>?" },
  "content": "<uploadId>", "thumb": "<uploadId>?", "preview": "<uploadId>?", "deviceId": "<16–64 [A-Za-z0-9_-]>?" }
```

Response: `{ node }` with `head` set to the new revision.

The server checks that every referenced upload is this account's, pending, unexpired, of the right purpose and **complete**. That means:

- `pg`: every chunk index is present with the exact sizes.
- `s3`: the bucket listing under the blob prefix matches the chunk count and sizes exactly, with no stray objects.

Otherwise `409 incomplete`. On success the blobs become immutable (`live`).

A new revision supersedes the previous one. At most `versionKeep` (10) older versions are kept, and the oldest beyond that are deleted at once.

Errors:

- `409 conflict` (+`node`) for a stale `baseVersion`.
- `409 exists` when `baseVersion = 0` but the node exists.
- `409 trashed`.
- `404 not_found`.
- `404 no_upload` when the upload is unknown, foreign or already committed. An upload can be committed exactly once.

Retrying a successful commit (same `nodeId` and `rev.id`) is idempotent.

### 4.5 Downloads

**`get`**: `POST /api/drive?a=get&b=<blobId>&i=<index>` with an empty body → the raw ciphertext chunk (`application/octet-stream`). It works for `pg` blobs and, as a proxy fallback, for `s3` blobs. Only committed blobs of the account can be read.

**`download.urls`** (for `s3` blobs): `{ blobId, from?: 0, count?: 1..200 }` → `{ urls: [{ i, size, url, method: 'GET' }], expiresIn }`. These are presigned GET URLs, valid for `ONE_PRESIGN_TTL` (900 s).

**`thumbs`**: `{ ids: blobId[] (≤ 100) }` → `{ thumbs: { "<blobId>": "<base64 of the sealed chunk>" } }`. Unknown or foreign ids are simply missing. Use this for timeline grids.

### 4.6 Trash and versions

**`trash`**: `{ nodeId, baseVersion? }` → `{ count, node }`

- The node and its whole subtree that is not yet trashed get `trashedAt` and `trashRoot = nodeId`.
- Items in the trash still count against the quota and stay downloadable.
- Trashing an already trashed node is a no-op.

**`restore`**: `{ nodeId }` → `{ count, node }`

- Restores the node plus everything that was trashed **together with it** below it.
- If its parent no longer exists or is still in the trash, the node is restored to the root (`parent: null`).

**`delete`** (delete forever): `{ nodeId }` → `{ count }`

- Only for trashed nodes; anything else gets `409 not_trashed`. This keeps deletion explicit and two-step.
- The node and its subtree that was trashed with it become *tombstones* (`deleted: true`, `key`/`meta`/`head` null). Revisions, blobs and chunks are deleted, and the quota is freed immediately.

**`trash.empty`**: `{ confirm: true }` → `{ count }`. Items in the trash are deleted forever automatically after `trashDays` (30).

**`versions`**: `{ nodeId }` → `{ node, versions: Revision[] }`. The current version comes first (`head: true`), then the others, newest superseded first.

**`version.restore`**: `{ nodeId, revId, baseVersion }` → `{ node }`. The old revision becomes current again, and the previous current one becomes an old version.

**`version.delete`**: `{ nodeId, revId }` → `{ deleted }`. Deleting the current revision returns `409 is_head`.

Old versions are deleted `versionDays` (30) after they were superseded, or when more than `versionKeep` (10) exist, whichever comes first.

### 4.7 Albums

**`album.put`**: `{ albumId, baseVersion: 0, key, meta }` creates an album (an identical retry is idempotent). `{ albumId, baseVersion: n, meta }` renames it. Both return `{ album }`. A stale version returns `409 conflict` (+`album`).

**`album.delete`**: `{ albumId }` → `{}`. Creates an album tombstone; the photos themselves are untouched.

**`album.items`**: `{ albumId, add?: uuid[], remove?: uuid[] }` (≤ 500 together) → `{ added, removed }`

- Only existing non-folder nodes of the account are added. Others are skipped silently.
- Removals become `Member` entries with `removed: true` in the feed.
- When a node is deleted forever, its memberships disappear without a member tombstone. Clients drop memberships that point to deleted or unknown nodes.

### 4.8 Backup status

**`backup.report`**:

```json
{ "deviceId": "<16–64 [A-Za-z0-9_-]>", "status": "idle|running|paused|error", "pending?": 0, "pendingBytes?": 0,
  "success?": true, "error?": "<[a-z0-9_]{1,40}>", "meta?": "<device envelope §5.6>" }
```

Response: `{ device: { deviceId, status, lastSuccessAt } }`.

- Send `success: true` after a backup run that left nothing pending.
- Every report updates `lastAttemptAt`. Only `success` updates `lastSuccessAt`.
- At most 50 devices per account.

**`backup.list`**: `{}` → `{ warnDays: 3, now, devices: [{ deviceId, meta, status, pending, pendingBytes, error, lastSuccessAt, lastAttemptAt, createdAt, updatedAt, stale }] }`

`stale` is true when the last success (or the device's creation, if it never succeeded) is older than `warnDays`. The UI **must** warn about stale devices (product principle "visible, provable backup").

**`backup.forget`**: `{ deviceId }` → `{ deleted }`.

### 4.9 Duplicates and export

**`dedupe`**: `{ hashes: string[] (≤ 200) }` → `{ matches: { "<hash>": [nodeId, …] } }`. Only current versions of nodes that are not trashed are matched. Use it in photo backup to skip what is already stored.

**`export`**: `{ after?: uuid|null, limit?: 1..500 = 200 }` → `{ version: 1, nodes: Node[] /* each with revisions[] */, albums: Album[] | null, next: uuid | null, emergency? }`

- Returns every live node, trash included, ordered by id, with **all** revisions and their blob layouts. Follow `next` until it is null.
- `albums`, including their `items`, comes only on the first page (`after` absent).
- `emergency` (first page only): the owner's Notfallzugang as in `em.status` `own` (setup, contacts, open request, **full** log) plus `covered: { nodes: uuid[], albums: uuid[] }`, or `null`. The web app writes it into the export as `Notfallzugang.json` and `manifest.json` → `emergency`.
- See §7.8 for building the "export everything" archive.

### 4.10 `gc` (operators only)

`GET` or `POST /api/drive?a=gc` with `Authorization: Bearer $CRON_SECRET` → `{ taken, deleted, failed }`. It deletes bucket objects of deleted S3 blobs from `private.fale_one_gc`. It is a no-op with `BLOBSTORE=postgres`.

## 5. Crypto (normative, format v1)

The primitives are AES-256-GCM (128-bit tag, 96-bit IV), HKDF-SHA-256 and HMAC-SHA-256, all via WebCrypto. The prefix `V` is the ASCII string `fale-one-v1`. `|` is a literal byte 0x7C, and AAD/info strings are UTF-8. Ids appear in their lowercase UUID form, and indices and counts in decimal.

### 5.1 Root: the FaLe-Konto master key (MK)

FaLe One uses the **same** 32-byte master key as FaLe Sync (`js/sync/crypto.js`).

- MK is created on the first device, wrapped by the Sync-Passwort (PBKDF2-SHA256, ≥ 600 000 iterations) and by the printable recovery key, and stored as `sync_keys` (Supabase RPC `sync_status` / `sync_keys_put`, called directly with the user token).
- A FaLe One app on another origin bootstraps like this:
  1. Sign in.
  2. Call `rpc('sync_status')`.
  3. If `key` is null: `createKeys(userId, password)` → `sync_keys_put(…, 'create')`, then show the recovery key once.
  4. Otherwise: `unwrapMaster(userId, key, { password } | { recovery })` → `importMaster(raw)`, then wipe `raw`.
- MK is kept only as a non-extractable HKDF `CryptoKey` (IndexedDB). Losing the password and the recovery key means losing the data. There is no server-side recovery, by design.

### 5.2 Account keys

```
salt = "fale-one-v1|<userId>"
KEK  = HKDF(MK, salt, info "fale-one-v1/kek")     → AES-256-GCM      wraps node and album keys
DK   = HKDF(MK, salt, info "fale-one-v1/dedupe")  → HMAC-SHA-256     keyed content hash
DVK  = HKDF(MK, salt, info "fale-one-v1/device")  → AES-256-GCM      backup device envelopes
```

`deriveKeys(mk, userId)` in `js/one/crypto.js`.

### 5.3 Item keys and file keys (random, wrapped)

```
NK (node key)  = 32 random bytes per node (folder/file/photo); immutable for the node's lifetime
AK (album key) = 32 random bytes per album
FK (file key)  = 32 random bytes per REVISION

node.key  = wrap(KEK, NK, AAD "fale-one-v1|wrap|node|<userId>|<nodeId>")
album.key = wrap(KEK, AK, AAD "fale-one-v1|wrap|album|<userId>|<albumId>")
rev.key   = wrap(FWK, FK, AAD "fale-one-v1|wrap|file|<userId>|<nodeId>|<revId>")   with FWK = HKDF(NK, salt "", info "fale-one-v1/filewrap")
wrap(K, raw, AAD) = base64url( 0x01 ‖ IV(12, random) ‖ AES-GCM(K, raw, AAD) )      → 61 bytes, 82 characters
```

The random keys, as opposed to keys derived from MK, are deliberate. They allow sharing a single node or album later by handing out NK, AK or FK without exposing MK. They also allow re-keying a node by uploading a new version under a new FK.

### 5.4 Envelopes (metadata)

```
envelope(K, json, AAD) = base64url( 0x01 ‖ IV(12, random) ‖ AES-GCM(K, UTF-8(JSON.stringify(json)), AAD) )

node.meta  : K = HKDF(NK, "", "fale-one-v1/meta"),  AAD "fale-one-v1|meta|<kind>|<userId>|<nodeId>"   kind = folder|file|photo
album.meta : K = HKDF(AK, "", "fale-one-v1/meta"),  AAD "fale-one-v1|meta|album|<userId>|<albumId>"
rev.meta   : K = HKDF(FK, "", "fale-one-v1/rmeta"), AAD "fale-one-v1|rmeta|<userId>|<nodeId>|<revId>"
```

Because the server-visible `kind` is in the AAD, the server cannot turn a photo into a file or a folder.

**JSON schemas (v1).** Unknown fields must be preserved on rewrite and ignored on read.

```jsonc
// node.meta – folder
{ "v": 1, "name": "Urlaub 2026", "color": "#…"? }
// node.meta – file / photo (changes on rename or EXIF edit; sent with commit or update)
{ "v": 1, "name": "IMG_2041.HEIC",
  "takenAt": "2026-07-14T10:22:00+02:00"?,   // photo: capture time with offset (timeline key)
  "tz": "Europe/Berlin"?, "w": 4032?, "h": 3024?, "orientation": 1?, "durationMs": 0?,  // video/live photo
  "gps": { "lat": 54.1, "lon": 7.9, "alt": 3.2 }?, "exif": { "make": "…", "model": "…", "iso": 100, … }?,
  "live": "<nodeId of the paired video>"?, "favorite": true?, "hidden": true?, "tags": ["…"]?,
  "faces"?: […], "labels"?: […]               // on-device ML results, never computed on the server
}
// rev.meta – per version
{ "v": 1, "size": 3145728 /* plaintext bytes */, "mime": "image/heic", "mtime": 1768000000000 /* ms */,
  "digest": "<hex SHA-256 tree digest §5.7>", "thumb": { "mime": "image/jpeg", "w": 256, "h": 192 }?, "preview": { "mime": "image/jpeg", "w": 1600, "h": 1200 }? }
// album.meta
{ "v": 1, "name": "Sommer", "cover": "<nodeId>"?, "sort": "taken"|"added"? }
// backup device envelope (DVK, AAD "fale-one-v1|device|<userId>|<deviceId>")
{ "v": 1, "name": "Annas Pixel", "platform": "android", "app": "1.0.0" }
```

**Timeline.** The server knows nothing about capture dates; not even a coarse month is stored in plaintext. The client builds the timeline from the decrypted `takenAt` (falling back to `rev.meta.mtime`) of the nodes it received through the change feed. It keeps that index locally, encrypted at rest if it is persisted.

### 5.5 Blobs and chunks (content, thumbnail, preview)

```
BK      = HKDF(FK, salt "<blobId>", info "fale-one-v1/blob/<purpose>")        purpose = content|thumb|preview
plainChunk = chunkSize − 28
chunks  = max(1, ceil(plainSize / plainChunk));  cipherSize = plainSize + 28 · chunks   (empty file: 1 chunk of 28 bytes)
chunk i = IV(12, random) ‖ AES-GCM(BK, plain[i·plainChunk … (i+1)·plainChunk), AAD) ‖ (tag inside GCM output)
AAD     = "fale-one-v1|chunk|<userId>|<nodeId>|<revId>|<blobId>|<purpose>|<i>|<chunks>|<1 if i = chunks−1 else 0>"
```

The AAD binds each chunk to its account, node, revision, blob, purpose, position and total count, and marks the final chunk. Reordering, swapping chunks between objects, truncation and extension are therefore all detected (see tests).

A fresh random IV is used per encryption, so retrying or resuming a chunk after the source file changed can never reuse a nonce.

**Thumbnails.** JPEG (or WebP) with a long edge of 256 px (default), stripped of EXIF. The sealed chunk must not exceed `thumbMaxBytes` (128 KiB), so the plaintext is at most 131 044 bytes; aim for ≤ 30 KB. A thumbnail is a single chunk with purpose `thumb`.

**Previews.** A larger JPEG/WebP (long edge 1600–2048 px; video: poster frame), purpose `preview`, ≤ `previewMaxBytes`. HEIC/RAW/video previews are rendered **on the device**. Both are optional.

### 5.6 Device envelope

See the JSON schema in §5.4 (`sealDeviceMeta`).

### 5.7 Content digest and keyed dedupe hash

```
digest = SHA-256( SHA-256(seg_0) ‖ SHA-256(seg_1) ‖ … ),  seg_k = plaintext[k·4 MiB … (k+1)·4 MiB)   (one segment for an empty file)
hash   = base64url( HMAC-SHA-256(DK, "fale-one-v1|dedupe|" ‖ digest) )   → 43 characters, stored as rev.hash
```

The digest goes into `rev.meta.digest` (hex), and the download verifies it. `hash` lets the server detect that **one account** stores the same content twice.

Without DK the server cannot compute the hash or test a guess ("does this user have file X?"). It cannot link equal files across accounts either. It does learn equality among the account's own files, which is accepted for the "skip duplicates" feature.

### 5.8 What is authenticated, what is not

- Content, names and metadata are confidential and authenticated.
- These server-visible values are **not** cryptographically bound:
  - the tree shape (`parent`)
  - `trashedAt`
  - album membership
  - the server-side ordering of versions
  - which revision is `head`
- A malicious server could therefore move, hide, resurrect or roll back items, but it could not forge or alter their content.
- Clients should treat moves they did not expect as normal sync, and show the version history.

| Download bytes per day | 50 GiB per account, 100 GiB per IP | `ONE_DOWNLOAD_DAILY_MB`, `ONE_IP_DOWNLOAD_DAILY_MB` |

The IP limits use a salted, day-scoped hash of the address, and IPv6 addresses are reduced to their /64 prefix. The limits share the `fale_rate` counters with the share feature, and the days follow Europe/Berlin.

**The quota counts everything:** current files, old versions, the trash, open uploads (reserved at `upload.create`), and keys plus envelopes. Counters are maintained by triggers, so a check costs O(1).

**Over quota means read-only, never deletion.** When `used ≥ quota`, any action that would add bytes returns `507 quota_exceeded`: `upload.create`, `mkdir`, `album.put` for create or growth, and envelope growth in `commit`/`update`.

Everything else keeps working:

- download
- list and feed
- move, or rename without growth
- trash and restore
- delete forever and versions
- export
- backup status

No purge ever depends on the quota. The UI should show a calm banner along the lines of "Speicher voll – alles bleibt lesbar; lösche, leere den Papierkorb oder exportiere", and **no** upsell nagging.

## 7. Client algorithms

`js/one/api.js` implements all of these; the steps below are the contract that other clients (native apps) must follow.

### 7.1 Start

1. `config()`. If `configured` is false, hide FaLe One.
2. Sign in to the FaLe-Konto (Supabase Auth, `js/account/auth.js`) and get the access token.
3. Get MK (§5.1), then `keys = deriveKeys(MK, userId)`.
4. `quota()` gives the chunk size, limits, `readOnly` and `cursor`.
5. Run the feed sync (§7.4).

### 7.2 Upload a new file or photo

1. `nodeId = uuid()` and `revId = uuid()`. Persist both *before* uploading, so the upload can resume.
2. `digest = contentDigest(file)`, then `hash = dedupeHash(keys, digest)`. For photo backup, call `dedupe([hash])` first and skip if there is a match.
3. `{key: NK, wrapped} = createNodeKey(keys, nodeId)`, then `{key: FK, wrapped: revKey} = createFileKey(NK, {userId, nodeId, revId})`.
4. `lay = layout(file.size, chunkSize)`, then `upload.create({purpose:'content', size: lay.cipherSize, chunks: lay.chunks, hash})` → `uploadId`.
5. `BK = blobKey(FK, uploadId, 'content')`. For each `i` (in parallel, 3 at a time recommended):
   - `sealChunk(BK, ctx, i, chunks, plain_i)`.
   - Then either `upload.put(uploadId, i, bytes)`, or, when `direct`, `PUT` to the presigned URL from `upload.urls`.
6. Thumbnail and preview (optional): render on the device, then repeat steps 4–5 with purpose `thumb`/`preview`, each with its own upload id, under the same FK.
7. `meta = sealMeta(NK, {userId, kind, id: nodeId}, {v:1, name, takenAt, …})` and `revMeta = sealRevMeta(FK, {userId, nodeId, revId}, {v:1, size, mime, mtime, digest: hex(digest)})`.
8. `commit({ nodeId, parentId, kind, baseVersion: 0, key: wrappedNK, meta, rev: { id: revId, key: revKey, meta: revMeta, hash }, content, thumb?, preview?, deviceId })`.
9. Apply the returned node locally. It also arrives through the feed, which is idempotent.

**Resume after a crash or app kill.** Persist `{nodeId, revId, wrapped NK, wrapped FK, uploadIds, file reference}`. Reopen FK with `openFileKey`, call `upload.status(uploadId)`, and send only the chunks missing from `received`. Re-encrypting a chunk is safe because every encryption uses a fresh IV.

If the session expired (`404 no_upload`), start the blob again with a new `upload.create`. Keep `revId` and FK, but give the new upload id to `blobKey`. A commit retry after a network error is idempotent.

**New version of an existing file.** Use `baseVersion = node.version` and the existing NK (`openNodeKey`), and a **new** `revId` and FK. `key` may be omitted. Send `meta` only if the name or EXIF changed.

On `409 conflict` (edited elsewhere meanwhile), the response carries the current node. Do not silently overwrite. Either:

- commit again as a new version on top (`baseVersion = conflict.node.version`), which keeps both in the version history, or
- save the local file as a new node named "… (Konflikt <Gerät> <Datum>)", which shows both.

Both choices are visible in the UI ("two versions, pick one").

### 7.3 Download

1. `NK = openNodeKey(keys, node.id, node.key)`, then `FK = openFileKey(NK, {userId, nodeId, revId: head.id}, head.key)`, then `revMeta = openRevMeta(…)`.
2. Pick the blob by purpose, then compute `BK = blobKey(FK, blob.id, purpose)`.
3. For each chunk `i < blob.chunks`, get the bytes:
   - `pg`: `get(blob.id, i)`.
   - `s3`: `download.urls`, then GET the URL.

   Then `openChunk(BK, ctx, i, blob.chunks, bytes)`.
4. Concatenate the chunks. Verify `revMeta.size` and `contentDigest == revMeta.digest`. On mismatch, show "Datei beschädigt" and never hand out partial data as complete.

For timeline grids, call `thumbs(ids)` in batches of 100, then `openSmall(FK, {…, blobId, purpose:'thumb'}, bytes)`. Cache the decrypted thumbnails locally.

### 7.4 Sync (change feed)

```
state: cursor (persisted), local index nodeId → decrypted node, albums, memberships
loop: r = changes(cursor, 500)
  if r.reset: wipe the local index; cursor = 0; continue
  for c in r.changes (ordered by seq):
    node   → if c.deleted: remove it locally (and from albums), else upsert (decrypt meta and head lazily)
    album  → if deleted: remove the album and its memberships, else upsert
    member → set/unset membership (album, node)
  persist the index THEN cursor = r.cursor
  until !r.more
```

- Poll when the app starts and resumes, after own writes, and every 30–60 s while visible. There is no push yet.
- Every write response returns the new node. Apply it immediately, and do not advance the cursor past entries you have not pulled.
- Items in the trash arrive with `trashedAt` set. The UI shows them only in the trash view.
- To rebuild a tree: `parent` points to a folder id, and `null` is the root. If a parent is unknown (it is still being paged in), keep the node pending until the page ends.

### 7.5 Delete and trash UX

- **Remove from this device** is a local action only (photo backup: the default is "backup mode", so deleting on the phone does **not** delete the cloud copy).
- **Delete** calls `trash`. **Delete forever** (only from the trash view) calls `delete` and needs a confirmation. **Undo** calls `restore`.
- After 30 days the server deletes trashed items. Show "wird am <Datum> endgültig gelöscht" (`trashedAt + trashDays`).

### 7.6 Photo backup (set-and-forget)

On each run:

1. Enumerate new media since the last run. For each item: digest, then hash; batch `dedupe(hashes ≤ 200)` and skip the matches.
2. Upload as in §7.2 (`kind: 'photo'`, `takenAt`/GPS/EXIF in the node meta, thumbnail and preview).
3. Report progress with `backup.report({deviceId, status: 'running', pending, pendingBytes})`. At the end, report `{status: 'idle', pending: 0, success: true}`, or `{status: 'error', error: '<code>'}`.

Show "Letzte Sicherung: vor 3 Min · 0 wartend" from `backup.list()`. Warn prominently when a device is `stale` (more than 3 days without a successful backup).

### 7.7 Albums

Create an album like this:

1. `albumId = uuid()` and `createAlbumKey`.
2. Seal `{v:1, name}`.
3. `album.put({albumId, baseVersion: 0, key, meta})`.

Rename with `album.put({albumId, baseVersion: album.version, meta})`. Add and remove photos with `album.items`.

### 7.8 Export everything ("leave anytime")

1. Page through `export` until `next` is null.
2. For each live node, decrypt the meta and download all revisions (or only the current one, if the user chooses).
3. Write `Ordner/Pfad/Name` with `mtime`. For photos, add an EXIF sidecar `<name>.json` (`takenAt`, GPS, EXIF) and a folder per album.
4. Add `manifest.json`: `{ exportedAt, account, nodes: [{ id, path, kind, versions: [{ id, size, mime, mtime, digest }] }], albums: [{ name, items: [path] }] }`.
5. Stream the result into a ZIP (`js/zip.js`) or a directory (File System Access API).
6. Make the export resumable by node id.

The export is plain data, so no FaLe tool is needed to read it.

### 7.9 Share a file by link (until there is native sharing)

The existing zero-knowledge share feature is reused, and no new endpoint is needed:

1. Download and decrypt the node (§7.3) into a `Blob`.
2. Get `ck = contentKey(newLinkKey(), kdf?, password?)` from `js/share/crypto.js`.
3. `uploadEncrypted(blob, { ck, kdf, meta: { name, type, size }, announce: o => shareApi.create({ ...o, kind: 'file', expiresIn, maxDownloads }) })`, then `shareApi.finish(id, auth)` (`js/share/api.js`; `shareApi.create` adds the device token itself). The link key and password handling are the same as in `js/share/create.js`.
4. The link is `https://fale-pdf.vercel.app/#/s/<id>#k=<base64url link key>`, the same as "Sicher teilen". The key stays in the fragment and never reaches a server. It is limited to `SHARE_MAX_MB` (50 MB) and expires after at most 7 days.

A later native "share folder/album" can hand out NK or AK wrapped for the recipient (ECDH, as in `js/smart/famcrypto.js`) without re-uploading. The key hierarchy in §5.3 is designed for that.

### 7.10 Account deletion

`POST /api/account?a=delete` (existing) removes all FaLe One rows, including chunks and the account counters, inside `fale_account_delete`. With S3 it also removes the bucket objects; leftovers are cleared by the gc worker. Before deleting, the UI should offer "export everything" first.

| | `BLOBSTORE=postgres` (default, beta) | `BLOBSTORE=s3` (Hetzner Object Storage) |
|---|---|---|
| Content and previews | `public.one_chunks` (bytea, TOAST external, no compression) | Bucket objects `<S3_PREFIX>/<userId>/<blobId>/<i>` (opaque ids only) |
| Thumbnails | Postgres | **Postgres** (small objects; Hetzner bills < 64 KB as 64 KB) |
| Upload | via API (`upload.put`) | direct with presigned PUT (`upload.urls`); API proxy as fallback |
| Download | via API (`get`) | direct with presigned GET (`download.urls`); API proxy as fallback |
| Commit check | SQL counts chunk rows and sizes | API lists the prefix (ListObjectsV2); SQL compares sizes |
| Deletion | rows cascade at once | trigger → `private.fale_one_gc` → `gc` worker deletes objects |

The switch is env only:

```

S3_ENDPOINT=https://fsn1.your-objectstorage.com
S3_BUCKET=fale-one
S3_REGION=eu-central
S3_ACCESS_KEY_ID=…

S3_PATH_STYLE=1

ONE_PRESIGN_TTL=900
CRON_SECRET=…
```

- Private, no public ACLs.
- CORS for the FaLe One origins: `PUT` and `GET` allowed, the request header `Content-Length` allowed, and the response header `ETag` exposed.

The gc worker can be scheduled with Vercel Cron by adding the following to `vercel.json`; the Hobby plan allows daily jobs only:

Private tables:

- `private.fale_one_config`: limits, see §6.
- `private.fale_one_totals`: global bytes per backend.

- `private.fale_one_seq`: the feed sequence.

Access:

- RLS is enabled on every table, there are **no policies**, and anon/authenticated have **no privileges**. Direct PostgREST access to the tables is therefore denied.

- deletes trash older than 30 days forever (as tombstones)
- deletes old versions
- deletes expired upload sessions
- deletes tombstones after 30 days, moving `min_cursor` past them
- deletes backup records silent for a year

Over-quota accounts are not touched. Account deletion: `fale_account_delete` was redefined to also delete all `one_*` rows.

## 10. Threat model

| Adversary | Can | Cannot |
|---|---|---|
| Server / DB operator, DB or bucket breach, subpoena | See account ids, counts, ciphertext sizes and chunk layouts, timestamps, tree shape and album membership (ids), equality of an account's own files (keyed hash), backup heartbeats and the IP-hash counters. Delete or withhold data, roll back to an older state, move or hide items (§5.8). | Read names, metadata, EXIF/GPS, thumbnails or content. Forge or modify content undetected. Test whether a user has a known file (needs DK). Link files across accounts. |
| Other FaLe users | Use the API with their own token. | Read, list, write, enumerate or probe foreign ids: every RPC is scoped to the verified user id, and foreign ids answer exactly like unknown ones (`404`). |
| Network attacker | Nothing beyond TLS metadata (sizes, timing). | Read content; presigned URLs expire after 15 min and are bound to one object (and, for PUT, to an exact length). |
| Stolen access token (≤ 1 h) | Use the account's API: list encrypted items, download ciphertext, upload, trash. Deleting forever needs the item in the trash first, and the trash keeps it for 30 days. | Decrypt anything (needs MK, which needs the Sync-Passwort or the recovery key and never leaves the devices). |
| Compromised device or malicious app version | Everything that device can do: MK is on it. | This is out of scope of the server design. Mitigations are a strict CSP, self-hosted scripts (no third-party CDNs), the review process, and device revocation (`fale_device_revoke`). |
| Abuse (free storage, DoS) | | Exceed the quota, the daily request/chunk/byte limits (per account and per IP /64), the global Postgres cap, 256 open uploads, 24 h session lifetime or the 4 MiB chunk/256 KiB JSON body limits. |

Hardening details:

- Strict input validation in the API (ids, base64url, integer ranges) **and** again in SQL.
- No user enumeration.
- The cron secret is compared in constant time (SHA-256 plus `timingSafeEqual`).
- Errors never echo internal details.
- Logs contain only error class and code, never tokens, ids or content.
- Anonymous Supabase sessions are refused.

## 12. Notfallzugang (emergency access to chosen items)

An owner names 1–3 trusted contacts (other FaLe-Konto users) and a waiting period. A contact can ask for access at any time; the owner sees it at once (banner on the next start, e-mail when a notifier is configured) and can deny it with one tap. If the waiting period passes without a veto, the contact gets **read-only** access to exactly the covered items and decrypts them on their own device. The owner can revoke at any time, and every request, veto, release, key pick-up, opening and download is logged for the owner. Optional "k of n": at least k contacts must ask together.

### 12.1 Keys and formats (normative: `js/one/crypto.js`)

```
Identity key   ECDH P-256 per account – the SAME key as the family folders of FaLe PDF (public.fam_keys):
               kid = b64u(SHA-256("<x>.<y>")[0..12]); private PKCS#8 wrapped by AES-GCM(HKDF(MK, salt <userId>, "fale-fam-priv-v1"),
               AAD "fale-fam|priv|v1|<userId>"). Clients check that the delivered public key matches the private key (ECDH self-test).
EK             32 random bytes per setup (setupId = client-generated lowercase uuid)
owner copy     setup.ownerKey = wrap(KEK, EK, AAD "fale-one-v1|wrap|em|<ownerId>|<setupId>")
covered keys   em key of a node/album = wrap(HKDF(EK, salt <setupId>, "fale-one-v1/em/wrap"), NK|AK,
               AAD "fale-one-v1|em|wrap|<node|album>|<ownerId>|<setupId>|<id>")          (82 chars like every wrapped key)
scope          envelope(HKDF(EK, salt <setupId>, "fale-one-v1/em/scope"), { v: 1, mode: "items"|"all", roots: [nodeId], albums: [albumId], note? },
               AAD "fale-one-v1|em|scope|<ownerId>|<setupId>")
check          b64u(HMAC-SHA-256(HKDF(EK, salt <setupId>, "fale-one-v1/em/check"), "fale-one-v1|em|check|<ownerId>|<setupId>"))   43 chars
seal (ECIES)   eph = new P-256 key; K = HKDF(ECDH(eph, recipientPub), salt = eph public key (65 bytes raw),
               info "fale-one-v1/em/seal|<purpose>|<setupId>|<toUserId>") → AES-256-GCM,
               AAD "fale-one-v1|em|seal|<purpose>|<ownerId>|<setupId>|<fromUserId>|<toUserId>"
               → b64u(0x01 ‖ eph(65) ‖ IV(12) ‖ GCM(UTF-8 JSON))        purpose: share (owner → contact) | pool (contact → contact)
Shamir         byte-wise over GF(2^8) with the AES polynomial 0x11b; x = contact slot (1..3); fresh random coefficients per split;
               k = 1 → every share is EK itself
package        seal(share, { v: 1, t: "share", setupId, ownerId, slot, x, k, n, y: b64u(share), check, roster: [{ slot, id, kid }] })
pool entry     seal(pool,  { v: 1, t: "pool", setupId, from: slot, x, y })
safety code    h = SHA-256("fale-one-v1|em|sas|<setupId>|<ownerId>|<ownerKid>|<contactId>|<contactKid>");
               6 emoji = h[0..6] as 48 bits, 6 bits each, into the 64-entry list SAS_EMOJI; digits = (h[6..12] as 48-bit integer) mod 10^12 → "1234 5678 9012"
```

**New files stay accessible.** Node keys are random and immutable for a node's lifetime, and a node's key opens all of its revisions (FK is wrapped by NK). Children's keys are wrapped by the account KEK, not by the parent folder's key, so wrapping a folder key alone would not reach new children. Instead, the owner's devices keep the server's set of EK-wrapped keys equal to the wanted set: every node in the covered subtrees (or every node and album for `mode: "all"`), the covered albums and their members. They do this after every sync; a local digest makes it free when nothing changed, and `em.keys.digest` makes it one request when only the server might differ. Files uploaded by any of the owner's devices are therefore wrapped within one sync. Trashed or deleted items disappear for the contact at once (server filter, FK cascade), and items moved out of the covered folders lose their wrap on the owner's next sync.

### 12.2 States

```
contact:  invited ──accept (same e-mail, identity key)──▶ accepted ──owner compares the safety code + seals──▶ active
request:  (none) ──first contact asks──▶ waiting ──k contacts asked: release_at = now + wait──▶ … ──now ≥ release_at──▶ released
             waiting ──owner denies──▶ denied (contacts may ask again after 24 h)        waiting|released ──owner revokes──▶ revoked
             waiting below k for 30 days ──▶ expired        re-seal while waiting ──▶ canceled
```

The waiting period starts when **k** contacts have asked (for k = 1: with the request), so the owner always gets the full period after the request that can actually unlock anything. A contact who joins an already released request gets access at once (logged). Release is evaluated lazily by every RPC and every 15 minutes by `fale-em-tick` (pg_cron), which also queues the notifications.

### 12.3 Actions (`POST /api/drive?a=em.*`)

Rate limits: `ONE_EM_DAILY` (2 000 per account, `ONE_EM_IP_DAILY` 4 000 per IP), invitations `ONE_EM_INVITE_DAILY` 10 (+ IP 30), requests `ONE_EM_REQUEST_DAILY` 20 (+ IP 60); chunk downloads count against the normal download limits of the **contact**.

| Action | Body → response | Who |
|---|---|---|

### 12.4 Client algorithms (`js/one/api.js`)

- **Set up** (`emCreate`): `emIdentityEnsure` (open or create the identity key), random EK and setupId, `em.setup`. The web app then creates the guided "Notfallordner" (sub-folders: contracts & insurance, powers of attorney & directives, bank & account notes, doctors & medication, contacts, personal wishes & letters) and runs `emSyncKeys`.
- **Confirm a contact** (`emReseal`): after both sides compared the safety code, split EK with a **fresh** polynomial for all active contacts plus the confirmed one (if k exceeds the confirmed contacts, extra x values are evaluated and discarded; requests stay impossible until k are active), seal each package with the roster and the check value, `em.seal`.
- **Keep keys current** (`emSyncKeys`): wanted set → digest → if different, list, wrap the missing NK/AK under EK (`openItemKeyRaw` → `emWrapItem`), delete the extra ones.
- **Unlock** (`emUnlock`, contact): `em.package`, open the package, check setup/owner/slot. For k > 1, seal the own share for every released requester **whose slot, account id and key id are in the owner's roster** and whose delivered public key hashes to that key id, `em.pool`, open the pooled shares addressed to us, then try k-subsets until the combined key matches `check` (a forged share is detected, never used). Not enough shares yet → `{ waiting: { have, need } }`.
- **Read** (`emLoad`, `emDownload`): `em.items`, open each node key with EK and decrypt meta, revision metadata, thumbnails and content exactly like the owner (AAD uses the owner's user id), content digest verified.

### 12.5 Notifications

The SQL functions write events into `private.fale_em_outbox` (invite, accepted, request, denied, released, revoked, confirmed, removed, left, ended). `api/_lib/notify.js` sends them after each `em.*` action and in the `gc` cron when a provider is configured: `NOTIFY_PROVIDER=resend` (+ `RESEND_API_KEY`, `NOTIFY_FROM`) or `NOTIFY_PROVIDER=webhook` (+ `NOTIFY_WEBHOOK_URL`, optional `NOTIFY_WEBHOOK_SECRET` → `X-Fale-Signature` HMAC). Mails contain only e-mail addresses, times and the app URL (`FALE_ONE_URL`), never names or content. Without a provider (the default – Supabase's built-in SMTP only sends Auth mails, and without custom SMTP only to team addresses) nothing is sent, `config.notify` is false and the app says so: requests appear as a non-dismissable banner the next time the owner opens FaLe One, and the invitation screen offers a ready-made message to send yourself. Unsent events are dropped after 14 days.

### 12.7 Threat model (honest)

| Who | Can | Cannot |
|---|---|---|
| Server / DB operator, breach | See who invited whom (e-mail addresses), which node/album ids are covered, the request/veto/release/view/download log, timestamps. **Release a package early**: the waiting period is enforced by this server. Withhold or delete the setup (availability). | Read EK, a share, a node key, names or content – packages are sealed for the contact's key, covered keys are wrapped by EK. With k > 1, an early release still needs k colluding contacts. |
| A contact | After a release: read and keep everything covered (that is the point – choose people you trust). | Read anything before a release, anything outside the covered items, or change anything (read-only: no write path exists). With k > 1: anything alone. |
| Key substitution (MITM by the server) | Hand the owner a wrong contact key, or a contact a wrong owner key id. | Go unnoticed: owner and contact compare the safety code over both key ids before the owner seals; pooling only goes to keys in the owner's verified roster; a forged share fails the check value. |
| Revoked / removed contact | Keep what was already downloaded (FaLe cannot take it back). | Fetch anything after the revocation: the server stops serving at once. Start the setup again ("beenden" + new setup) for a new EK after a release, if needed. |
